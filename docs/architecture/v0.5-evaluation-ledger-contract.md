# KODIT v0.5 설명가능 판정 원장 계약

상태: 설계 기준선(Draft)  
적용 대상: KODIT 규정 공개현황  
후속 단계: 별도 DB migration 초안 및 rollback형 계약 테스트  

## 1. 목적과 비목표

v0.5의 목적은 화면의 상태 플래그를 `정의 → 입력 근거 → 실행 → 체크 결과 → 파생 결과 → 변경 이력 → 공개 스냅샷`으로 재현할 수 있게 만드는 것이다.

이번 계약은 다음을 금지한다.

- 신뢰도 숫자로 개별 체크의 PASS/FAIL을 역산하는 것
- 과거에 존재하지 않았던 실행·게이트 이력을 소급 생성하는 것
- 공개상태, 현행성, 생애주기, 문서검증, 미공개 단계와 신뢰도를 하나의 종합점수로 합치는 것
- Discord, SQL 관리자 또는 화면에서 결과 상태나 신뢰도를 직접 지정하는 것
- Ollama 반복 실행을 독립 공식출처 또는 검색엔진 수로 계산하는 것
- 수집·재검증 결과를 자동으로 published/latest release로 승격하는 것

현행성 및 생애주기의 완전한 자동 판정 게이트는 v0.5의 별도 설계 과제로 남긴다. 정의되지 않은 산식을 임의로 구현하지 않는다.

## 2. 축별 루브릭(Rubric)

### 2.1 공개상태 `availability`

공개상태는 등급이 아니라 상호배타 분류다. 판정 우선순위는 다음과 같다.

1. `EXTRACTION_PENDING` — 필수 수집·추출·동일성 확인 미완료
2. `ACCESS_UNAVAILABLE` — 확인된 URL을 정해진 재시도 정책 후에도 열 수 없음
3. `FULLTEXT_PUBLIC` — 공식 경로 원문과 전문 공개 필수조건 충족
4. `PARTIAL_PUBLIC` — 일부 실질 내용은 공개됐지만 전문 요건 미충족
5. `SOURCE_UNKNOWN` — 후보 파일은 있으나 공식 원출처 연결 실패
6. `NOTICE_ONLY` — 공식 사전예고는 있으나 전문 미발견
7. `NONPUBLIC` — 필수 조사와 사람 최종확인 완료
8. `NONPUBLIC_CANDIDATE` — 전문 미발견이나 최종 검증 미완료

필수 불변조건:

- `NOTICE_ONLY`이면 공개 가능한 `primary_evidence_url`이 반드시 존재해야 한다.
- `NOTICE_ONLY`의 기본 클릭 대상은 공식 사전예고 게시물 또는 공식 첨부다.
- HWP/HWPX는 다운로드, magic bytes 및 SHA 확인만으로 `FULLTEXT_PUBLIC`이 될 수 없다.
- `EXTRACTION_PENDING`은 미공개 확정으로 승격될 수 없다.
- 공개상태로 현행성 또는 생애주기를 추론하지 않는다.

### 2.2 주장 신뢰도 `confidence` 1~5

신뢰도는 주장별 AND 게이트다. 퍼센트나 가중평균이 아니며 모든 적용 필수조건을 충족한 최고 레벨을 파생한다. `N/A`는 criterion의 적용 제외 사유가 기록된 경우에만 PASS와 동등하게 취급한다.

| 레벨 | 표시 | 필수 criterion |
|---:|---|---|
| 1 | 미검증 | C1 주장·대상 식별 및 재검증 가능한 발견경로 |
| 2 | 후보 | C1 + C2 추적 가능한 근거 1개 이상 |
| 3 | 유력 | 1~2 + C3 공식 언급·대상·일자 기본 매칭 |
| 4 | 검증 | 1~3 + C4 1차 공식 원문 + C5 다운로드·형식·SHA·본문 + C6 원문의 주장 직접 지지 |
| 5 | 확정 | 1~4 + C7 필요한 기간·대상·적용범위 확인 + C8 중대한 상충자료 없음 또는 해소 |

`human review`가 필요한 criterion은 C7/C8 또는 주장 유형별 추가 criterion으로 명시한다. 버튼 클릭 자체가 PASS를 만들 수 없고, 검토 이벤트와 근거가 criterion 결과를 생성해야 한다.

파생 결과에는 최소한 다음이 포함된다.

- `derived_confidence_level`
- `decisive_criterion_code`: 다음 레벨 상승을 막은 가장 우선적인 criterion
- `failed_criterion_codes`
- `pending_criterion_codes`
- `reason_code`
- `reason_short`
- `official_source_count`
- `search_verification_count`
- `human_confirmed`

`n/m`은 진행 표시일 뿐 신뢰도 계산에 사용하지 않는다.

### 2.3 미공개 검증 `nonpublic_stage`

미공개 단계는 공개상태와 별개의 조사 진행도다.

| 단계 | 코드 | 조건 |
|---:|---|---|
| 1 | `ANOMALY` | 10일 내부수집에서 전문 미발견 |
| 2 | `REPLICATED` | Grok에서도 전문 미발견 |
| 3 | `PROBABLE` | Gemini에서도 동일 결과 |
| 내부 게이트 | `DEEPSEEK_NO_FIND` | DeepSeek에서도 신규 전문 후보 없음 |
| 내부 게이트 | `OLLAMA_RUN_1_COMPLETE` | Ollama 1차 재현 완료 |
| 내부 게이트 | `OLLAMA_RUN_2_COMPLETE` | Ollama 2차 재현 완료 |
| 검토 대기 | `HUMAN_REVIEW_REQUIRED` | 두 Ollama 실행 모두 신규 후보 없음 |
| 4 | `CONFIRMED` | 전체 이력과 원문을 사람이 확인 |

DeepSeek 또는 Ollama에서 신규 전문 후보가 발견되면 단계 상승을 즉시 중단하고 `EXTRACTION_PENDING` 흐름으로 되돌린다. URL 접근, 다운로드, SHA 및 본문 검증을 새로 수행한다.

Ollama 2회는 같은 로컬 계열 모델을 이용한 재현성 검사다. 따라서 다음 값은 분리한다.

- `search_verification_count`: Grok/Gemini/DeepSeek 중 완료된 독립 검색엔진 수(0~3)
- `ollama_verification_count`: 요구조건을 충족한 Ollama 재현 실행 수(0~2)
- `official_source_count`: 공식출처 수
- `human_confirmed`: 사람 최종확정 여부

### 2.4 현행성 `currentness`

- `CURRENT_CONFIRMED` — 현재 적용본임이 확인됨
- `HISTORICAL` — 후속 개정·대체본이 확인된 과거본
- `CURRENT_UNKNOWN` — 공개본은 있으나 현재 최종본인지 확인되지 않음

자동 게이트가 승인되기 전에는 `CURRENT_CONFIRMED`를 자동 생성하지 않는다. `FULLTEXT_PUBLIC`은 현행 확정의 근거가 아니다.

### 2.5 생애주기 `lifecycle`

- `CURRENT`
- `HISTORICAL`
- `ABOLISHED`
- `MERGED`
- `UNKNOWN`

생애주기는 공개상태 및 현행성과 독립적이다. 자동 게이트가 승인되기 전에는 기존 명시 근거 또는 사람 검토로만 상태를 생성한다.

### 2.6 문서검증 `document_verification`

문서검증은 하나의 혼합 코드가 아니라 다음 체크를 각각 저장한다.

- `DOWNLOAD`
- `MAGIC_FILETYPE`
- `SHA256`
- `EXTRACTION`
- `BODY_ANCHOR`
- `HUMAN_OPEN`

각 체크 결과는 `PASS / FAIL / PENDING / N_A` 중 하나다. `EXTRACTION_PENDING`, `NOTICE_EVIDENCE_ONLY` 같은 판정 사유 또는 근거유형을 문서검증 상태값으로 사용하지 않는다. 화면용 문서검증 요약은 이 체크들에서 파생한다.

## 3. 파생 규칙(Derivation)

### 3.1 유일한 산출 경로

권위 있는 결과는 내부 함수 `core.derive_kodit_evaluation(evaluation_run_id)`만 생성한다. 함수는 고정 `search_path`를 사용하고, 서비스 수집기 및 검증 작업자만 실행할 수 있어야 한다.

함수의 입력은 다음으로 제한한다.

- 잠긴 methodology version
- 해당 evaluation run의 실제 criterion 결과
- run에 연결된 공개·내부 근거 참조
- 실행 provenance와 기준시각
- 유효한 인간 검토 이벤트

직접 입력한 결과가 파생값과 다르면 DB가 거절해야 한다. `claims.confidence_level`, 현재 상태 캐시 또는 공개 snapshot을 진실의 원본으로 삼지 않는다.

### 3.2 신뢰도 산출 의사코드

```text
for level in 5 down to 1:
  required = applicable required criteria through level
  if every required result in {PASS, N_A(with reason)}:
    return level

return 1
```

다음 레벨의 필수 criterion 중 `FAIL` 또는 `PENDING`이며 우선순위가 가장 높은 항목을 `decisive_criterion_code`로 기록한다. 배열 전체에는 모든 실패·대기 criterion을 보존한다.

### 3.3 결과와 실행의 불변성

- 완료된 evaluation run, criterion result 및 execution event는 append-only다.
- 재검증은 기존 run을 수정하지 않고 새 run을 만든다.
- methodology 변경은 과거 결과를 재작성하지 않는다.
- 승인 release의 projection 및 공개 gate snapshot은 UPDATE/DELETE할 수 없다.

## 4. Provenance와 실행시각

### 4.1 `provenance`

- `LEGACY_DERIVED`: 과거 결과값만 존재하며 historical gate check가 없음
- `ACTUAL_EXECUTION`: 해당 시점에 실제 실행된 수집·검증·엔진·사람 검토
- `RECONSTRUCTED_EVALUATION`: 보존 자료를 이후 시점의 방법론으로 다시 평가

### 4.2 필수 시각

- `executed_at`: 코드·엔진·평가 또는 검토가 실제 수행된 시각
- `evidence_as_of`: 해당 평가가 사용한 근거의 기준시각
- `recorded_at`: 원장에 기록된 시각

예를 들어 2026-09-08까지 확보된 자료를 2026-09-13에 Ollama로 재검증했다면 다음과 같이 기록한다.

```text
provenance   = RECONSTRUCTED_EVALUATION
executed_at  = 2026-09-13T...
evidence_as_of = 2026-09-08T...
engine       = ollama
```

`LEGACY_DERIVED`에는 실제 실행을 나타내는 가짜 `executed_at`이나 criterion 결과를 생성하지 않는다.

## 5. 평가·실행 이력(Evaluation history)

기존 테이블은 유지하고 다음 계층을 추가하는 방향으로 migration을 설계한다.

### 5.1 `core.evaluation_runs`

평가 한 번의 경계다.

```text
evaluation_run_id
claim_id
methodology_version
provenance
executed_at
evidence_as_of
recorded_at
initiated_by_type       SYSTEM / SERVICE / HUMAN
initiated_by_ref
supersedes_run_id
run_status              RUNNING / COMPLETED / FAILED / CANCELLED
derivation_version
```

### 5.2 `core.evaluation_check_results`

```text
evaluation_check_result_id

criterion_id
result                  PASS / FAIL / PENDING / N_A
required_value
actual_value
reason_code
reason_short
evidence_document_sha256
evidence_url_id
checked_at
checked_by_type
checked_by_ref
```

완료 후 UPDATE/DELETE를 금지한다. `N_A`에는 `reason_code`가 필수다.

### 5.3 `core.evaluation_results`

파생 함수가 작성하는 append-only 결과다.

```text
evaluation_result_id
evaluation_run_id UNIQUE
availability_code
derived_confidence_level
currentness_code
lifecycle_code
document_verification_summary
nonpublic_stage
nonpublic_phase
decisive_criterion_code
failed_criterion_codes
pending_criterion_codes
reason_code
reason_short
official_source_count
search_verification_count
ollama_verification_count
human_confirmed
derived_at
```

현행성·생애주기의 자동 규칙이 없는 동안에는 `CURRENT_UNKNOWN`/`UNKNOWN` 또는 별도 명시 근거가 있는 결과만 허용한다.

### 5.4 실행 trace 연결

`core.evaluation_execution_links`가 evaluation과 기존 실행 원장을 연결한다.

```text
evaluation_run_id
execution_type          CRAWL / DOCUMENT_VALIDATION / SEARCH_ENGINE / OLLAMA / HUMAN_REVIEW
execution_id
sequence_no
relation                INPUT / SUPPORT / CONTRADICTION / DECISION
```

이를 통해 `crawl_runs`, 문서 검증 실행, `verification_runs`, Ollama 실행 및 인간 검토를 규정·주장 단위 timeline으로 구성한다.

## 6. Ollama 실행 계약

Ollama는 판정자가 아니라 재현 검증 엔진이다. 실제 구현 시 기존 `verification_runs`를 확장하거나 동일한 공통 실행 원장을 사용한다.

필수 기록값:

```text
engine_name = ollama
model_name
model_digest
prompt_version
prompt_sha256
input_evidence_sha256
attempt_no            1 / 2
started_at
completed_at
result_code           NO_NEW_FULLTEXT / CANDIDATE_FOUND / ERROR
parsed_candidate_urls
raw_response_internal
provenance
executed_at
evidence_as_of
```

Ollama 1·2차는 서로 다른 `attempt_no`와 실행 ID를 가져야 한다. 후보 발견 시 미공개 상승을 중지한다. raw response와 내부 경로는 공개 API에 포함하지 않는다.

## 7. 인간 검토와 Discord 인터페이스

### 7.1 `review_channel`

- `WEB_WORKBENCH`
- `DISCORD`
- `SQL_ADMIN`
- `SYSTEM`

`review_channel`은 provenance가 아니다. 예를 들어 Discord에서 실제 실행 결과의 후보를 채택하면 다음과 같다.

```text
provenance    = ACTUAL_EXECUTION
review_channel = DISCORD
reviewer_type = HUMAN
action        = ACCEPT_CANDIDATE
```

### 7.2 `core.human_review_events`

```text
human_review_event_id
evaluation_run_id
review_channel
reviewer_type          HUMAN / SYSTEM
reviewer_subject_id
action                 ACCEPT_CANDIDATE / REJECT / REQUEST_REVISION / REQUEST_REVERIFY
reason_code
reason_text
evidence_refs
created_at
external_interaction_id_hash
```

외부 interaction ID는 중복 처리 방지를 위해 해시로 저장한다. Discord 표시명만으로 reviewer를 식별하지 않고 내부 승인 사용자와 연결한다.

### 7.3 인간 검토 대기열과 trigger

`human_review_required`와 `human_confirmed`는 서로 다른 값이다. `human_confirmed = false`, 미확정 건수 또는 release의 DB 승인 전 상태를 인간 검토 대기로 계산하지 않는다. 자동·엔진 검증을 완료한 뒤 명시적인 `review_trigger`가 발생한 항목만 인간 검토 대기열에 포함한다.

release 승인 상태도 개별 항목 검토와 분리한다.

```text
release_approval_status = 번들 전체의 공개 승인 상태
human_review_required   = 개별 항목에서 현재 사람의 조치가 필요한지
human_confirmed         = 특정 주장 또는 미공개 단계의 사람 최종확정 여부
```

제안 테이블 `core.human_review_triggers`:

```text
human_review_trigger_id
evaluation_run_id
claim_id
trigger_code
trigger_reason_code
trigger_reason_short
status                  OPEN / CLAIMED / RESOLVED / CANCELLED
created_at
claimed_at
resolved_at
resolution_event_id
```

허용하는 최초 trigger code:

- `HUMAN_DOCUMENT_INSPECTION`: 자동 추출·대체 PDF·재시도를 모두 완료했으나 문서 확인 실패
- `HUMAN_NONPUBLIC_CONFIRMATION`: 모든 외부 엔진과 Ollama 2회가 신규 전문을 찾지 못해 최종 단계 승격 필요
- `HUMAN_SOURCE_CONFLICT`: 공식 원출처 후보가 둘 이상 충돌
- `HUMAN_IDENTITY_RESOLUTION`: 규정명·별칭 매칭을 자동으로 확정할 수 없음
- `HUMAN_MISMATCH_REVIEW`: legacy 결과와 v0.5 재평가 결과가 충돌

`EXTRACTION_PENDING`, `NOTICE_ONLY`, `SOURCE_UNKNOWN`만으로 trigger를 생성하지 않는다. 각 상태의 자동 처리 경로가 소진되었을 때만 해당 trigger를 생성한다. Discord 검토 이벤트는 열린 trigger를 참조해야 하며, trigger 해소 결과가 다시 파생 함수를 통과해야 한다.

현재 v0.5 재평가 전 화면은 인간 검토 필요 건수를 숫자로 단정하지 않고 `미산정`으로 표시한다. 작업량은 다음 큐로 분리한다.

- 자동·엔진 검증 대기
- 문서처리 재검증
- 미공개 검증
- 원출처 탐색
- 인간 검토 필요(명시적 OPEN trigger 수)

### 7.4 Discord 허용 및 금지

Discord는 판정엔진이 아니라 human-review interface다.

허용:

- 후보·근거·실행이력 조회
- Ollama 추가질문 요청
- 재검증 요청
- 후보 채택
- 반려
- 수정 요청

금지:

- `core` 상태 직접 지정
- `confidence_level` 직접 지정
- `claim_check` PASS 강제
- `human_confirmed` 직접 변경
- release 자동 공개승격

Discord action은 검토 이벤트만 생성한다. 서비스가 권한, 중복, 현재 run 상태 및 필수 게이트를 검증한 뒤 새 evaluation 결과를 파생한다. 후보 채택만으로 원장 상태가 바뀌지 않는다.

Discord bot token 및 webhook secret은 서버 환경변수에만 두고 브라우저, DB 공개열, 로그, artifact 및 저장소에 기록하지 않는다.

## 8. Legacy 보존과 v0.5 재평가

기존 1,041건은 다음과 같이 보존한다.

```text
derivation = LEGACY_DERIVED
legacy_confidence_level = 기존 1/2/4 값
historical_gate_checks = 없음
legacy_methodology_version = v0.4
```

v0.5 전환은 과거 이력을 복원하지 않는다. 전환 시점에 현재 확보된 문서·URL·SHA 및 실행 이력을 입력으로 새 `RECONSTRUCTED_EVALUATION` run을 실행한다.

```text
evaluation_run = v0.5 전환 시각
executed_at = 실제 재평가 시각
evidence_as_of = 재평가에 사용한 근거 기준시각
criterion C1..Cn = 실제 PASS/FAIL/PENDING/N_A
derived_confidence_level = 파생 결과
```

### 8.1 `core.legacy_evaluation_comparisons`

comparison_id

claim_id
legacy_methodology_version
legacy_result_code
legacy_confidence_level

## 9. 공개 스냅샷(Public snapshot)

### 9.0 `EXTRACTION_PENDING` 182건 측정 기준선

2026-09-13 읽기 전용 측정에서 2026-09-08 검토본의 `EXTRACTION_PENDING` 182건은 모두
`ole_error:AttributeError`라는 동일한 실패 시그니처를 보였다. 이는 단일 공통 근본원인
가설을 강하게 지지하지만, 182건이 하나의 근본원인이라는 뜻은 아니다. 원인이 파서 코드,
실제 파일 포맷 불일치, 다운로드 또는 파일 손상, DRM·미지원 형식 중 무엇인지는 대표 표본의
magic bytes, 원본 SHA-256, 전체 stack trace와 당시 parser/package/version을 확인한 뒤 확정한다.

이 기준선의 기존 실행에는 parser 식별 정보가 없으므로 `parser_name`과 `parser_version`을
`UNKNOWN`으로 보존한다. 측정만으로 인간 검토 trigger를 만들지 않으며, 표본 진단 → 소규모
canary → 전체 재처리 → 잔여 residual 재분류 순서를 따른다. 파싱 성공은 전문 공개 판정이
아니며, 규정명·별칭·본문 구조 검증과 별도 재평가가 필요하다.

측정 산출물과 실행 manifest는
`reports/measurements/2026-09-13-pending-182/`에 보존한다.

공개 API는 최신 `published + is_latest` release의 immutable snapshot만 반환한다. 현재 상태 원본이나 draft를 직접 읽지 않는다.

기존 `core.release_regulation_rows`와 함께 승인 시점의 설명 projection을 고정한다.

제안 테이블:

```text
core.release_regulation_check_rows
- release_id
- regulation_code
- claim_type
- criterion_code
- criterion_label
- result
- reason_code
- reason_short
- public_evidence_label
- public_evidence_url
- checked_at

core.release_regulation_timeline_rows
- release_id
- regulation_code
- event_type
- engine_label
- result_code
- occurred_at
- provenance
- evidence_as_of
- public_summary
```

공개 projection에는 다음을 포함하지 않는다.

- 검색엔진·Ollama raw response
- 내부 프롬프트 전문
- 비공개 문서 경로 및 storage path
- Discord 사용자 ID·채널 ID·메시지 ID
- 내부 오류 원문
- 사건정보 또는 개인정보

화면과 CSV는 같은 공개 snapshot 배열을 사용한다. CSV에는 최소한 결과 코드, 짧은 사유, 결정 criterion, 실패·대기 criterion, 방법론 버전, provenance, 평가시각과 근거 기준시각을 포함한다.

## 10. 계약 테스트(Contract tests)

후속 migration은 최소 다음 rollback형 테스트를 통과해야 한다.

1. 신뢰도 숫자를 직접 지정하면 거절된다.
2. C1~C6 PASS, C7 PENDING이면 신뢰도 4이고 decisive criterion은 C7이다.
3. 같은 체크 결과에서 보조 진행률이 달라져도 신뢰도는 변하지 않는다.
4. `N_A`에 사유가 없으면 거절된다.
5. `FULLTEXT_PUBLIC`이어도 현행성은 자동으로 `CURRENT_CONFIRMED`가 되지 않는다.
6. HWP/HWPX 다운로드·SHA만으로 `FULLTEXT_PUBLIC` 생성이 거절된다.
7. `EXTRACTION_PENDING`은 미공개 최종단계로 상승하지 못한다.
8. `NOTICE_ONLY`에 공개 가능한 사전예고 근거 URL이 없으면 거절된다.
9. DeepSeek/Ollama에서 후보가 발견되면 미공개 단계 상승이 중지된다.
10. Ollama 2회를 공식출처 수 또는 검색엔진 수에 더하지 않는다.
11. Ollama 2회 완료만으로 `human_confirmed`가 생성되지 않는다.
12. Discord 후보 채택만으로 상태·신뢰도·human confirmation이 바뀌지 않는다.
13. `human_confirmed=false` 또는 DB 승인 전이라는 이유만으로 인간 검토 trigger가 생성되지 않는다.
14. 자동 처리 경로가 남아 있는 `EXTRACTION_PENDING`, `NOTICE_ONLY`, `SOURCE_UNKNOWN`은 인간 큐에 포함되지 않는다.
15. 명시적인 OPEN trigger만 인간 검토 필요 건수에 포함된다.
16. 유효한 인간 검토 이벤트와 필수 게이트가 모두 있을 때만 최종 파생이 가능하다.
17. `ACTUAL_EXECUTION`과 `RECONSTRUCTED_EVALUATION`은 서로 다른 실행시각·근거 기준시각을 보존한다.
18. `LEGACY_DERIVED`에 가짜 historical gate check를 생성할 수 없다.
19. v0.5 재평가는 기존 v0.4 결과를 UPDATE하지 않는다.
20. legacy와 v0.5 결과 차이는 구조화된 comparison 행을 만든다.
21. 완료 run·check·result·review event는 UPDATE/DELETE할 수 없다.
22. published snapshot과 설명 projection은 UPDATE/DELETE할 수 없다.
23. 공개 RPC에서 draft, raw response, 내부 경로, Discord 식별자 및 사건정보가 0건 노출된다.
24. 화면 체크 표시는 공개 RPC의 실제 criterion 결과와 일치한다.
25. `NOTICE_ONLY` 클릭 대상은 snapshot의 공식 사전예고 URL과 일치한다.

## 11. migration 전 미정 항목

다음은 문서에 상태값은 있으나 자동 산식 또는 운영정책 승인이 필요하다.

- 현행성 `CURRENT_CONFIRMED` 자동 게이트
- 생애주기 자동 게이트 및 공식 폐지·통합 근거 우선순위
- Discord reviewer 내부 계정 연결 및 개인정보 보존기간
- Ollama 모델명·digest 고정 정책과 두 실행의 독립 조건
- 검색엔진 및 Ollama raw response 보존기간
- 공개 가능한 근거 URL과 내부 전용 URL 분류 규칙
- reason code 전체 사전과 다국어 표시 정책

이 항목이 미정인 동안 관련 결과는 `UNKNOWN`, `PENDING` 또는 사람 검토 대기로 유지한다.
